## Ways to contribute

You don't have to write code to help:

- **Report a bug** — an issue with a reproduction is genuinely useful.
- **Improve the docs** — if something in the README confused you, it will confuse someone else.
- **Add a test** — especially for behaviour that is documented but not yet covered.
- **Fix a bug or add a feature** — see [Proposing a feature](#proposing-a-feature) first if it changes the public API.

## Set up the project

You need **Node.js 22 or newer** and **pnpm 11**. The published package is browser-only and has no Node requirement — the floor comes from the test toolchain (jsdom 30).

If you don't have pnpm:

```bash
corepack enable
```

Then:

```bash
git clone https://github.com/abbas-roholamin/localpulse.git
cd localpulse
pnpm install
```

Verify the checkout is healthy before you change anything:

```bash
pnpm test
```

## The workflow

1. **Branch** off `main`:

   ```bash
   git checkout -b fix/storage-event-key
   ```

2. **Change** the code in `src/`, and the tests in `tests/`.

3. **Run the checks** — these are exactly what CI runs, so a green local run means a green PR:

   ```bash
   pnpm test        # vitest, jsdom environment
   pnpm typecheck   # tsc --noEmit
   pnpm build       # tsdown → dist/, validated with publint + attw
   ```

   While iterating, `pnpm test:watch` re-runs only what you touched.

4. **Add a changeset** if users would notice the change — see [Changesets](#changesets).

5. **Open a pull request** against `main`.

## Project layout

```
src/
  index.ts                        Public entry point — the only file that decides what is exported
  createLocalStorageObserver.ts   The observer: get/set/remove/subscribe/destroy
  serializer.ts                   JSON encode/decode, with unparsable values reading as null
  types.ts                        LocalStorageObserver, Listener, Unsubscribe
tests/                            One test file per source file, plus ssr.test.ts
assets/                           README images
.changeset/                       Pending changesets, consumed at release time
.github/workflows/                ci.yml (every push and PR) and release.yml (main only)
```

`dist/` is generated by `pnpm build` and is not committed.

Anything not re-exported from `src/index.ts` is internal and can change without a major version. If your change adds an export, it is public API — say so in the pull request.

## Writing tests

Tests run in **vitest** with the **jsdom** environment, which provides a real `localStorage` and real `storage` events.

- Put tests for `src/foo.ts` in `tests/foo.test.ts`.
- Clear storage between tests so cases don't leak into each other:

  ```ts
  beforeEach(() => localStorage.clear());
  ```

- Cross-tab behaviour can't be triggered by writing to `localStorage` directly — the browser only fires `storage` for *other* tabs. Dispatch the event yourself:

  ```ts
  window.dispatchEvent(
    new StorageEvent("storage", { key: "user", newValue: '{"id":1}' }),
  );
  ```

- Server-side behaviour belongs in `tests/ssr.test.ts`, which runs without a `window`.

Every bug fix should come with a test that fails before the fix and passes after it.

## Code style

There is no linter to argue with — `pnpm lint` is `tsc --noEmit`. Match the surrounding code:

- **Strict TypeScript.** No `any`, no non-null assertions, no `@ts-ignore`. `get()` and listener arguments are `T | null` and should stay that way.
- **No dependencies.** The package ships zero runtime dependencies, and that is a feature. Dev dependencies are fine if they earn their place.
- **Never throw at users.** Blocked storage, exceeded quota, corrupt JSON, and SSR all degrade quietly — reads return `null`, writes are skipped. Keep new code in that shape.
- **Guard browser globals.** `window` and `localStorage` are both checked before use; accessing `localStorage` throws outright in sandboxed iframes.
- **Comment the why.** The code explains what it does; comments exist for the reasons that aren't obvious from reading it.

Keep the bundle small. `pnpm build` prints the output size — if a change makes it meaningfully bigger, mention that in the pull request.

## Changesets

Any change users can notice — a bug fix, a new option, a behaviour change, a documented gotcha — needs a changeset:

```bash
pnpm changeset
```

Pick a bump level, write one sentence in the voice of a changelog entry, and commit the generated file in `.changeset/`:

- **patch** — bug fix, or docs that ship with the package
- **minor** — new API that doesn't break existing code
- **major** — anything that breaks an existing call site

Purely internal changes (tests, CI, this file) don't need one.

## Commits and pull requests

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

```
fix: notify subscribers when another tab clears storage
feat: expose the observed key as observer.key
docs: document Date round-trip behaviour
chore: bump vitest to 4.1
```

For the pull request itself:

- Keep it focused on one thing — a small PR gets reviewed faster than a big one.
- Describe **what** changed and **why**, and include a reproduction if it fixes a bug.
- Make sure `pnpm test`, `pnpm typecheck`, and `pnpm build` all pass.
- Include a changeset when the change is user-facing.

CI runs the same three commands on Node 22 and 24. Don't worry about squashing your history — the merge handles that.

## How a release happens

You don't need to publish anything; maintainers don't either. When a PR with a changeset lands on `main`, the release workflow opens a **"chore: version packages"** PR that bumps the version and updates `CHANGELOG.md`. Merging that PR publishes to npm via trusted publishing, tags the commit, and creates a GitHub release.

## Reporting a bug

Open an issue at [github.com/abbas-roholamin/localpulse/issues](https://github.com/abbas-roholamin/localpulse/issues) with:

- what you expected and what happened instead
- the `localpulse` version, plus browser or framework if it's relevant
- the smallest snippet that reproduces it

Before filing, check the [Behaviour worth knowing](./README.md#behaviour-worth-knowing) section — same-tab writes made directly through `localStorage.setItem` are not detected by design, and that one comes up often.

## Proposing a feature

Open an issue before writing code. `localpulse` deliberately stays small — one key, one observer, no dependencies — so the useful question is whether a feature belongs *in* the package or on top of it. The React hooks in the README are an example of the latter: documented, not shipped.

Describe the problem you hit rather than the API you want, and we'll find the smallest thing that solves it.
